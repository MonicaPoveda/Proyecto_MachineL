Project Title

Web System Based on Machine Learning for Phishing Detection

Problem Statement

Context and Rationale

1.1. Problem Context

Phishing is a cybersecurity threat that uses social engineering to deceive people and obtain confidential information through links that impersonate legitimate websites. Traditional solutions, which rely mainly on blacklists, have limitations when identifying new links or those that have not yet been reported.

In addition, many security tools do not clearly explain the risks associated with suspicious links or provide understandable recommendations to users. This situation highlights the need for solutions that can analyze links, identify risk patterns, and support the prevention of potential digital fraud through machine learning techniques.

1.2. Rationale

This project proposes developing a web-based machine learning system to support the early detection of phishing risk by analyzing lexical and structural URL features and Indicators of Compromise (IoC) data.

The intended population includes users who receive unfamiliar links and organizations or professionals that need an initial and understandable risk signal. Potential consequences include credential or personal-data theft, financial loss, unauthorized account access, and loss of trust in digital services.

The implemented solution complements traditional mechanisms by presenting a binary estimate, an estimated phishing probability, and an interpretable explanation of selected URL patterns. It also includes an optional HTTPS browser preview. The result is decision support, not a safety certification or a substitute for security software.

In this way, the project seeks to contribute to phishing prevention, strengthen users' digital security, and demonstrate the usefulness of machine learning in detecting potentially malicious links.

General Objective

Project Objective

Develop a machine-learning-based web system for URL phishing risk estimation and preview, in order to support cautious decision-making among users while clearly communicating the uncertainty and limitations of the prediction.

Specific Objectives

CRISP-DM Project Phases

01

Business Understanding

Define the system's functional and non-functional requirements, URL scope, user guidance, validation criteria, and success thresholds based on a review of background information and cybersecurity reports.

02

Data Understanding

Collect, explore, and analyze the dataset of Indicators of Compromise (IoCs) from datos.gov.co, along with samples of legitimate URLs from complementary sources, to identify structural patterns that distinguish malicious links from legitimate ones and evaluate data quality and class balance.

03

Data Preparation

Clean, normalize, and transform lexical and syntactic URL characteristics, prepare a balanced dataset, remove duplicates and invalid records, and create an 80/20 training-test partition for the machine learning model.

04

Modeling

Train, tune, and compare Logistic Regression, Random Forest, and Gradient Boosting with three-fold stratified cross-validation, and select the candidate with the highest mean F1 score.

05

Evaluation

Evaluate the selected model on the reserved test set using accuracy, phishing precision and recall, F1, ROC-AUC, false-positive rate, and the confusion matrix. Validate the authenticated web interface and browser preview against documented functional and security requirements.

06

Deployment

Implement the interactive web application by integrating the serialized predictive model, 31 URL features, authentication, result interpretation, and an HTTPS preview restricted to the user's browser.

Project Foundations

Theoretical Framework: From Reactive to Predictive Security

Designing a machine learning-based system to counter phishing requires moving from reactive responses toward predictive and adaptive mechanisms. Traditional blacklists rely on previously reported threats and may therefore lag behind short-lived fraud campaigns driven by social engineering.

01

Predictive Approaches

Data mining can analyze lexical and syntactic URL patterns to estimate risk without relying solely on a domain already appearing on a list of malicious sites. This approach aims to support the early identification of new or short-lived threats.

02

Technical and Methodological Foundations

Sahingoz et al. (2019) studied algorithms such as Random Forest and Support Vector Machines using lexical and syntactic URL features, reporting accuracy above 97% in their experiments, including for zero-day attacks. Jain and Gupta (2019) explored automated hyperlink feature extraction without relying on page content, avoiding the need to execute page scripts during analysis.

Silva et al. (2022) applied CRISP-DM and reported the performance of decision trees in controlled settings. These studies inform the model comparison and data workflow for this project.

03

Colombian Context and Open Data

Indicators of Compromise (IoCs) published on datos.gov.co provide an official source for studying threats associated with the Colombian landscape. Analyzing them may help contextualize the project data and identify local patterns; their availability and update frequency should be verified during dataset preparation.

04

Limitations of Current Solutions

Static blacklists may not include newly created domains. Multi-engine scanners can present technical results that are difficult to interpret, while some browser extensions provide limited explanations or control over the inspection of a suspicious link. These limitations particularly affect users without technical expertise.

05

Integrated System Proposal

The proposal combines three components to make diagnosis preventive, understandable, and user-focused:

Contextual Detection

Analyze 31 lexical and structural URL features and use IoC-derived examples during training. IoC data is not queried live for each submitted URL.

Actionable Guidance

Present the binary estimate, estimated probability, and available Random Forest path conditions while clearly stating that the result is not a safety guarantee.

Safer Link Preview

Load public HTTPS pages in a browser iframe with sandbox restrictions. This preview does not run on the Flask server and does not certify whether a site is safe.

Methodology and Development Schedule

Six-Phase CRISP-ML Process

The project was reorganized under CRISP-ML(Q) for this final consolidation. The previous CRISP-DM work remains the basis for business understanding, data preparation, modeling, evaluation, and deployment. CRISP-ML adds explicit quality assurance and monitoring and maintenance activities.

Phase Application in the project Status and evidence
1. Understanding the business and data Defined the URL-only phishing problem, scope, users, sources, risks, and success criteria. Documented in the methodological pages and project files. Interviews and formal user validation are not recorded.
2. Data engineering Filtered IoC URL/FQDN records, combined them with legitimate URLs, normalized and deduplicated records, balanced classes, extracted 31 features, and created an 80/20 partition. Implemented in the Phase 3 preparation script. The split is random and stratified, but it does not separate domains or periods.
3. Model engineering Compared Logistic Regression, Random Forest, and Gradient Boosting with parameter search and three-fold stratified cross-validation. Implemented in the Phase 4 modeling script. Random Forest had the highest documented mean F1.
4. Model evaluation Reported metrics, the confusion matrix, threshold comparison, overfitting risk, and generalization limitations. Documented for the balanced test set. Independent domain/time evaluation and formal specialist review remain pending.
5. Model deployment Integrated authentication, URL validation, model inference, estimated probability, an explanation, and an HTTPS browser preview. Implemented in Flask and configured for Gunicorn and Render. The published service must be verified before delivery.
6. Monitoring and maintenance Established a proposed process for availability, errors, feature drift, metrics, model updates, and rollback. A future plan is documented. Automatic metric measurement, label collection, drift detection, and retraining are not implemented.
