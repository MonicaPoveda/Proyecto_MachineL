Performance analysis of the Logistic Regression model against business objectives.

1. Model Overview

Algorithm: StandardScaler + Logistic Regression (main) / SVM (optional comparison)

Dataset: balanced_dataset_complete.csv (42,424 URLs)

Train/Test Split: 80% (33,935) / 20% (8,483)

Validation: StratifiedGroupKFold (5 folds), grouped by domain

Features: 31 URL characteristics (length, dots, hyphens, entropy, etc.)

Target: is_phishing (0 = Legitimate, 1 = Phishing)

Threshold: 0.5

3. Comparison with Business Objectives

From the Business Understanding phase, the acceptance criteria were:

Criterion Target Actual Result Status
Phishing Recall ≥ 0.80 0.7649 (76.49%) ❌ Not met
Phishing Precision ≥ 0.85 0.9370 (93.70%) ✅ Met
False Positive Rate ≤ 0.05 0.0514 (5.14%) ⚠️ Borderline

Conclusion: The model meets the Precision objective but fails to meet the Recall objective (76.49% vs. 80% required). This means it misses too many phishing URLs.

4. Confusion Matrix

Predicted: Legitimate Predicted: Phishing
Actual: Legitimate TN: 4,024 FP: 218
Actual: Phishing FN: 997 TP: 3,244

Interpretation: The model has 997 False Negatives (undetected phishing), which is the main security risk. It also has 218 False Positives (legitimate URLs flagged as phishing), which can cause unnecessary warnings.

5. Errors and Limitations

  • High False Negatives (997): The model misses 23.5% of real phishing URLs. This is the most critical issue.
  • Artificial Balance: The dataset is 50/50 balanced, but in the real world phishing is less frequent. This may inflate the Accuracy metric.
  • Linear Model Limitation: Logistic Regression is a linear model and may not capture complex non-linear patterns in phishing URLs.
  • No Prediction on New URLs: The current web app does not use the model to predict new URLs; it only looks up the dataset. This limits real-world applicability.
  • Threshold 0.5: A lower threshold would increase Recall but also False Positives.

6. Does the Model Solve the Problem?

Partially. The model is a good first layer of defense with 93.70% Precision, but its 76.49% Recall means it is not sufficient on its own to protect users. It should be combined with:

  • Blacklists (Tranco): To catch known malicious domains.
  • Human reporting (PhishTank): To cover new and unknown phishing URLs.
  • A non-linear model (Random Forest, XGBoost): To potentially improve Recall.

7. Should We Return to a Previous Phase?

Yes. It is recommended to return to the Modeling phase to:

  • Test a non-linear model (Random Forest, XGBoost) to improve Recall.
  • Adjust the decision threshold (e.g., from 0.5 to 0.3) to increase Recall at the cost of more False Positives.
  • Add more features related to URL structure and domain reputation.

Alternatively, return to the Data Preparation phase to collect more phishing samples that are currently missed by the model.

8. Final Model Selection

After evaluating the Logistic Regression model against the business objectives, the Logistic Regression model is selected as the final model for this phase, with the following justifications:

  • Strengths: High Precision (93.70%), interpretable, fast to train, and meets the Precision objective.
  • Weaknesses: Low Recall (76.49%), which fails the Recall objective (≥ 0.80).
  • Next steps: As recommended in Section 7, the model should be improved by testing non-linear algorithms or adjusting the threshold in a future iteration.

Final decision: The Logistic Regression model is accepted as a baseline model but requires improvement before deployment in a real-world production environment.
