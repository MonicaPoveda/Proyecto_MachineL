CRISP-ML(Q) Methodology · Phase 06 of 06

Monitoring and Maintenance

Define how the deployed phishing-risk classifier should be reviewed, maintained, and updated as data and threats change. This page documents a proposed operational plan; automated production monitoring is not currently implemented.

Current status

What is and is not monitored today

The web application serves URL predictions using the selected Random Forest and records application exceptions in its logs. It does not automatically collect ground-truth labels, measure production precision or recall, detect data or concept drift, or retrain the model. This distinction matters because the reported test metrics describe a balanced, randomly held-out dataset, not ongoing production performance.

Proposed monitoring plan

Signals for periodic human review

The following indicators are recommendations, not active alerts or established service-level thresholds. Review frequency and thresholds should be agreed by the project maintainers before operational use.

Review area Suggested indicators Response when a concern is found
Availability and errorsService availability, prediction failures, model-loading errors, and response-time trends.Investigate deployment configuration, dependencies, and model artifact availability before restoring service.
Input and feature driftChanges in URL formats and distributions of the 31 extracted features, measured without retaining raw URLs where possible.Check whether input changes reflect new legitimate formats, attack patterns, or a feature-extraction defect.
Classification qualityPrecision, recall, F1, false-positive rate, and confusion matrix on a recent labeled sample.Inspect false positives and false negatives, verify labels, and assess impact before changing thresholds or models.
Data quality and freshnessSource provenance, label definitions, duplicate rates, class balance, and the collection period.Resolve source or labeling issues and document any changes before the data is used for retraining.
Security and privacyAuthentication and access control for operational data, plus any logging or retention of submitted URLs.Limit access and retention to what is necessary; do not capture credentials or sensitive query values.

Controlled maintenance

Recommended model update and rollback process

  1. Collect or obtain a recent, representative dataset with reliable labels through an approved process; record source, time period, and known limitations.
  2. Validate the data, remove duplicates and invalid records, and review class prevalence and possible label leakage.
  3. Repeat the documented data-engineering and model-engineering steps using a training/validation strategy that separates domains and time where feasible.
  4. Evaluate the candidate with a separate recent test sample. Compare phishing recall, precision, false-positive rate, calibration where available, and error patterns with the deployed model.
  5. Require maintainer review and record the model, feature schema, training data provenance, metrics, and approval decision before deployment.
  6. Deploy the candidate in a controlled release, verify model loading and predictions, and retain the prior known-good artifact and configuration for rollback.
  7. If performance, availability, or safety concerns arise, revert to the prior version, investigate the cause, and document the incident and corrective action.
Not currently automated: production label collection, performance dashboards, drift detection, approval workflows, model version rollback, and automatic retraining are future operational work.

Quality assurance

Phase completion and handoff

For the project deliverable, this phase provides a documented monitoring and maintenance plan that complements the implemented, authenticated application. It does not claim that monitoring controls are operating. Operational data and commercial or sensitive information must remain protected behind authentication and appropriate access controls.
