CRISP-DM Methodology · Phase 06 of 06

Deployment

Deployment of the URL classifier in the web platform, with a plan to monitor its results, preserve its artifacts, and update it in a controlled manner.

Model implementation

Trained model and prediction loading

Models are trained outside the prediction request flow using the Phase 4 process. This process saves serialized models in outputs/phase4_output/models/, together with outputs/phase4_output/model_comparison.csv and outputs/phase4_output/modeling_metadata.json. The platform selects the model with the highest mean cross-validation F1; based on the current results, it selects Random Forest.

When the first request is received, the application loads the selected model and reuses it for subsequent requests. It does not retrain the model for each URL. The Phase 4 selection is preliminary: its cross-validation metrics do not replace the final evaluation using the reserved Phase 5 test set.

Application integration

URL analysis workflow

  1. An authenticated user submits a URL through the platform page.
  2. The application validates and normalizes the input, then extracts the features expected by the model.
  3. The model classifies the URL as possible phishing or probably legitimate and, when available, calculates an estimated phishing probability.
  4. The page displays the result and explanatory features. The classification is an estimate, not a guarantee that a website is safe.

If model artifacts are missing or the expected features do not match, the application reports that prediction is unavailable instead of generating a fallback result.

Using the results

Decision support

The result helps users decide whether to treat a URL with caution. A possible phishing alert should prompt them not to open the link or enter information; a probably legitimate result should not be interpreted as a safety certification.

The tool analyzes URL features and does not replace antivirus software, reputation lists, or a specialist investigation.

Monitoring

Proposed monitoring

  • Review application logs and prediction errors in Render.
  • Monitor availability, response times, and failed requests.
  • When ground-truth labels become available, periodically measure precision, recall, F1, and false negatives on new data.
  • Avoid logging or retaining submitted URLs unless there is a justified need and appropriate privacy controls.

Prediction exceptions are currently recorded in the application log; no system is configured to automatically measure production metrics or collect ground-truth labels.

Maintenance and updates

Controlled update process

  1. Collect recent examples with reliable labels and review their quality and representativeness.
  2. Retrain and compare the models using the documented Phase 4 process.
  3. Evaluate the candidate with the reserved test set and compare its metrics with the current version.
  4. Update the model and its metadata together; verify feature compatibility and test predictions before deployment.
  5. Keep a copy of the previous version so the update can be rolled back if errors or performance degradation are detected.

The service is configured for deployment on Render with Gunicorn. Render's default filesystem is ephemeral, so model artifacts must be included in the deployment or retrieved from persistent storage. The SQLite user database may also be lost on restart or redeployment; preserving user accounts requires a persistent database.
